DynaMem, the big picture

Four calls, two point clouds, and one rule that makes the memory “dynamic”.

Mission: read, run, and change DynaMem in this repo with confidence. This lesson gives you the map you will use for every later one: which file does what, and why the memory is built the way it is.

What DynaMem is

DynaMem is the open-vocabulary mobile manipulation stack in stretch_ai. You type “pick up the apple and place it on the plate” and the robot navigates to the apple, picks it, navigates to the plate, and drops it. The thing that makes it different from a static map is in the name: the memory is updated online, so objects that move, appear, or vanish are reflected without re-scanning the room.1

The paper reports a 70% pick-and-drop success rate on objects that were moved between scans, against 30% for the static predecessor OK-Robot.1 Keep that number in mind: nearly all of the code you will read exists to earn it.

The four calls

Every pick-and-place is the same four calls, in the same order. The repo's own documentation says so2, and the interpreter in dynamem_task.py hard-codes it: a ("pickup", A) command runs _find(A) then _pickup(A); a ("place", B) command runs _find(B) then _place(B).

There is a fifth call, explore(), which is navigate with an empty query: the robot goes wherever the memory says it is most worth looking, and updates as it goes.

Two point clouds, not one

This is the design decision to internalise. SparseVoxelMap keeps two voxelised point clouds, and they answer different questions.

voxel_pcd: the obstacle cloud Inherited from the base map. Points carry position and colour only. Voxel size is voxel_size = 0.10 m from dynav_config.yaml. It is flattened into a 2D grid of obstacles and explored cells that A* plans on, and into a history layer that drives exploration.
semantic_memory: the feature cloud Created in the DynaMem subclass. Every point also carries a vision-language feature vector (SigLIP on GPU, CLIP on CPU) and the id of the image it came from. Voxel size is 0.05 m on GPU. When you ask for “apple”, the text is embedded and dotted against every point's feature; the best point tells the robot where to go and which stored image to double-check with an object detector.

Why not one cloud? Because the two have opposite needs. Planning wants a dense, cheap, geometry-only grid. Grounding wants sparse points with expensive features attached. The code even subsamples them differently when adding a frame: the obstacle cloud keeps 10% of valid pixels, the semantic cloud keeps 5%.3

The rule that makes it dynamic

Look at process_rgbd_images in voxel_dynamem.py. For every new RGB-D frame it does, in order:

  1. voxel_pcd.clear_points(depth, K, pose), then add(...) new obstacle points.
  2. semantic_memory.clear_points(...), then add_to_semantic_memory(...) new featured points.

Clear before add. clear_points, in utils/voxel.py, projects every stored point into the new camera. A stored point is deleted if it lands inside the image, closer than 2.5 m, and the new depth image sees past it by more than 0.1 m. In words: if the camera can now see through the place where a point used to be, that point is gone. That is the paper's ray-casting removal rule1, and the ablation says it alone is worth about three points of success rate (70.6% with removal vs 67.8% without).

Everything else about the memory being “online” follows from this. The robot rescans after every 8 waypoints (process_text in the agent), and each rescan both removes stale points and adds fresh ones.
